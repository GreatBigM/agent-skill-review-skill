# 出库卫生：定档、历史收口、回读核验

审查/修复做完到「用户真的拿到新版」之间这一段，是泄漏与假验收最集中的地方。四件事。

## 一、定档的第二个坐标：出库状态

同一处残留，「本地工作树里有」与「已出库版本里有」是两档，而**档位只由出库版本决定**。

- 判据 = 对**出库版本**扫，不是对工作树扫：`git show <remote>/<branch>:<path>`；整仓用
  `git ls-tree -r --name-only <remote>/<branch>` 逐文件取正文再扫。
- **「仓库公开」（托管 API 返 200）只证明仓可见，不证明那行字已推上去**——实测据此把「潜伏」误定成
  「已在漏」，白紧张一轮。
- 出库版本也含 ⇒ **已在漏**：公开历史收不回，本轮只能保证「当前版本 + 未出库部分」干净，报告里写明这条。
- 只有未推送提交含 ⇒ **潜伏**，且有**零成本重写窗口**：修法用 `--amend` / `rebase` 重写那几笔，
  **严格优于「推完再补一笔」**（补一笔既收不回历史、又永久可查）。报告里写清窗口还剩多久。
- 扫出库版本时先剔合成值：闸门 `--self-test` 那批合成代号（`hm####` / `bw###` / `prj0##` 这类形态的假号）是自检样本，不是泄漏——**写这句时别把合成值照抄进来**，否则闸门会把说明文字本身打红（实测）。

## 二、推送前：未推送区间的收口

真名出现在**任何一笔将来会被推送的提交树里**，推上去就永久可查；**提交信息同样进公开历史，而且比树更毒**
（树能靠重写抹掉，信息一旦推送就是原文）。所以推送前要清的是「区间内每一笔提交的树 + 每一笔的提交信息」，
不是只看 HEAD，也不是只看工作树。

- **检查**：对区间内每笔提交扫它的树（`git grep -l -E '<模式>' <commit>`，或逐文件 `git show <commit>:<file>`），
  再 `git log --format=%B <base>..HEAD` 过一遍信息。**别把补丁文本当泄漏**——`git log -p` 显示的是 diff（删掉的旧行也在里面），**树才是事实**。
- **修法两条**：① 残留落到**引入它的那笔提交**（interactive rebase 标 `edit` → 改文件 → `--amend` → `--continue`）；
  ② 或把区间**压成一笔**（`git reset --soft <远端基> && git commit -F <新信息>`）——中间态全消失，最省事最稳，
  代价是丢提交粒度，用一条合并信息写清两类改动即可。
- **树一致性校验**（证明只改历史、没动内容）：改写前记下收口版的 `git rev-parse <HEAD>^{tree}`，改写后 `git rev-parse HEAD^{tree}` 必须相等。
  参照物**别用「改写前的 HEAD」**——若那笔自身就是要被改的（如含真名的闸门提交），参照物本身是错的；正确参照是**修复收口后的那次 HEAD**。
- **回滚锚**：改写前 `git update-ref refs/heads/bak/<name>-<ts> HEAD`。
- `--amend` 保留原作者信息；要换身份用 `--reset-author`——**该 flag 只能与 `--amend` / `-C` / `-c` 同用**，
  跟在普通 `git commit` 后面直接报错（此时 `reset --soft` 已落地，先看 HEAD 在哪再重来）。

## 三、扫描面之外的三个面（闸门 rc=0 覆盖不到）

闸门（`publish-check.py` 类）只扫「工作树里的文件正文」，以下三面永远扫不到，必须单独查：

| 面 | 为什么在扫描面外 | 单独怎么查 |
|----|------------------|-----------|
| `.git` 元数据 | `SKIP_DIRS` 含 `.git` 且 `os.walk` 剪枝 ⇒ 作者/提交者邮箱、commit message 永不进扫描面 | `git config user.email` + `git log --format='%ae' \| sort \| uniq -c`：公开仓必须全是 noreply 邮箱；公司域邮箱一旦推上去永久可查，只能改配置停止新增（历史里的若干笔收不回） |
| 被有意排除的扫描面 | 例：pre-push 的「改本体必须同步 CHANGELOG」名单**有意不含 README**（理由：README 是首页，随 CHANGELOG 一起看）⇒ README 侧的计数/术语残留永不被机械发现（实测：README 仍写「三项检查都跑」而钩子已 4 步） | 把「有意排除」写进判据句（连同代价），并在修复轮把该文件的陈旧计数当**固定人工检查项**过一遍 |
| 闸门自身 | 它在自己的 `SKIP_FILES` 里（正当理由：含规则字面量）⇒ 是「永不被自己扫、却随仓公开」的发布件 | 变体扫真仓：`SKIP_FILES=set()`（先 `assert` 变异落地）后扫真库，逐条列出即盲区内容 |

闸门自身这一面的三个后果（都实测过）：

1. **它的 docstring / 注释里的举例就是泄漏面**：写「旧版只认小写，`<真代号>` 整体漏」= 把真名放进公开仓，而扫真库永远 rc=0。
   修法：举例一律用**合成代号**（与自检样本同口径）；规则表里的数字签名是「必须枚举才能检出」的东西，
   写明「这是扫描签名表、不是举例」，免得下一轮被当泄漏重复报。
2. **「自检样本也会被扫描命中」在本仓实现下永远不成立**——样本就在这个被跳过的文件里。文档这么写
   （同条目又并列「闸门自身是唯一例外」= 自相矛盾）就报 P1；表述限定为「样本写在**闸门之外的**脚本里才会命中」。
3. **描述这次闸门修复的 CHANGELOG 条目是真名回潮的高发地**：写「旧版漏掉某某」时最顺手用真名，
   而它同时会进提交信息 ⇒ 未推送时必须一并清（见第二节）。

**维护闸门本体的两条纪律**：

- **别凭屏幕上的内容回写闸门文件**：工具输出会对 `Bearer <值>` / `password: <值>` 这类**自检样本本身**做脱敏显示
  （屏幕上变成 `***`），照显示回写会把样本改坏——症状是 `--self-test` 从「全部通过」变「该命中却放行」。
  改闸门用 `patch` / `cp`（别整文件重打），回写后第一件事跑 `--self-test`（它专验样本，正好接住这类自伤）。
- 文件头的「已知边界」段要把上面三面写全，别让读者以为「rc=0 = 干净」。

## 四、出库后回读核验（别把 push 的 rc 当证据）

1. `git fetch --all` 后比对**本地 / 主托管 / 镜像三端 HEAD 一致**（`git rev-parse gitee/main origin/main HEAD`）。
2. 用托管平台 API 取**线上文件正文**比哈希：`/api/v5/repos/<owner>/<repo>/contents/<path>?ref=<branch>` → base64 解码 → `md5sum`。
   **`raw` 端点返回的不是文件正文**（反爬：md5 对不上、`grep` 不到内容），回读一律走 API。
3. 出库版本再扫一遍泄漏模式（同第一节）。
4. 副本同步**必须在 push 之后**：`sync-audit.py --sync`（备份落扫描根之外），再**不带 `--sync` 重跑一次**确认「全部一致」才算收口。

## 收尾清单（照着勾）

- [ ] 每笔未推提交的**树**扫过、`git log --format=%B` 扫过
- [ ] 改写后 `HEAD^{tree}` 与收口版一致；备份 ref 已留
- [ ] `git config user.email` 是 noreply；出库历史里的公司域邮箱已在报告里写明（不可回收）
- [ ] 有意排除出扫描面的文件（README 等）人工过了一遍陈旧计数
- [ ] 推送时各仓自带钩子在跑（钩子输出「干净，可以发布」本身就是一条独立验收）
- [ ] 线上正文经 API 回读比对；副本已同步并重跑审计
